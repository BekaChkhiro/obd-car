# Data Handling Reference

Internal reference documenting every category of data the OBD-II AI Diagnostic
Assistant collects, where it lives, how long it is kept, and what controls exist.
Update this document whenever a new data category or retention policy is introduced.

---

## 1. Data categories

### 1.1 Account data

| Field | Location | Notes |
|---|---|---|
| Email address | Backend SQLite (`users.email`) | Normalised to lowercase. |
| Password hash | Backend SQLite (`users.password_hash`) | bcrypt; raw password never stored. |
| Google subject ID | Backend SQLite (`users.google_sub`) | OAuth link only; no Google profile data stored. |
| Locale preference | Backend SQLite (`users.locale`) | BCP-47 tag, e.g. `"en"`, `"ka"`. |
| Account created timestamp | Backend SQLite (`users.created_at`) | UTC. |

Account rows cascade-delete when the user calls `DELETE /auth/me`. All related
data (sessions, messages, tool calls, vehicles, refresh tokens) is removed in the
same transaction via SQLAlchemy `cascade="all, delete-orphan"`.

### 1.2 Authentication tokens

| Field | Location | Retention |
|---|---|---|
| Refresh token (SHA-256 hash only) | Backend SQLite (`refresh_tokens.token_hash`) | 30 days from issuance, or until revoked. |
| Access token | In-memory / secure client storage | 15 minutes TTL; never persisted server-side. |

Raw refresh tokens are never stored. The server stores only the SHA-256 hex
digest so a database breach does not expose reusable tokens.

### 1.3 Vehicle data

| Field | Location | Notes |
|---|---|---|
| Make, model, year | Backend SQLite + on-device SQLite | User-supplied. Optional; may be null. |
| VIN (17 chars) | Backend SQLite + on-device SQLite | Read from vehicle ECU or user-supplied. Optional. |
| Soft-delete timestamp | Backend SQLite (`vehicles.deleted_at`) | Supports offline sync; permanently removed on account deletion. |

Vehicles are synced bidirectionally between the on-device SQLite database and
the backend using last-write-wins (LWW) conflict resolution keyed on
`vehicles.updated_at`.

### 1.4 Diagnostic sessions

| Field | Location | Notes |
|---|---|---|
| Session ID | Backend SQLite + on-device SQLite | UUID. |
| Supported PIDs (JSON array) | Backend SQLite (`diagnostic_sessions.supported_pids`) | PID codes the connected adapter reported as available. |
| VIN snapshot | Backend SQLite (`diagnostic_sessions.vin`) | VIN at session start. |
| Session start / end timestamps | Backend SQLite | UTC. |
| AI context summary | Backend SQLite (`diagnostic_sessions.context_summary`) | Rolling text summary generated by the AI to keep long conversations within the token budget. Contains no raw PII beyond what the user typed. |

Sessions are not synced to the on-device database (the mobile schema tracks
session rows for UI purposes only; the server is authoritative for AI context).

### 1.5 Chat messages and tool calls

| Field | Location | Notes |
|---|---|---|
| Message role (`user` / `assistant` / `tool`) | Backend SQLite + on-device SQLite | — |
| Message content (plain text) | Backend SQLite + on-device SQLite | User-typed questions and AI replies. May contain vehicle symptoms, DTC codes, repair decisions. |
| Tool name | Backend SQLite + on-device SQLite | E.g. `read_pids`, `get_dtcs`, `clear_dtcs`. |
| Tool input / output (JSON) | Backend SQLite + on-device SQLite | Live OBD sensor readings, DTC lists, freeze-frame data. |
| Timestamps | Both | UTC. |

Chat content is sent to Anthropic's Claude API to generate AI responses. See
§ 3 (Third-party processors) for Anthropic's data terms.

### 1.6 Live OBD sensor readings

Live PID values (RPM, vehicle speed, coolant temperature, fuel level, battery
voltage, etc.) are read from the vehicle ECU over Bluetooth LE and streamed to
the Claude API within the current session. They appear as tool outputs in the
`tool_calls` table. **They are not stored separately** — only the tool call
record that contains them is persisted.

### 1.7 Bluetooth device information

The app uses the ELM327 adapter's BLE advertisement to discover and pair the
device. No Bluetooth device names, MAC addresses, or pairing keys are stored
persistently — only the session-level connection state held in memory.

### 1.8 Crash and error reports (Sentry)

| Data | Transmitted to | PII treatment |
|---|---|---|
| Stack traces, breadcrumbs, device model, OS version | Sentry (sentry.io) | Chat message content (`content`, `messages`, `system` keys) is scrubbed before transmission. `send_default_pii=False`. |

Sentry is optional. If `SENTRY_DSN` is not configured, no data is sent.

## 2. Storage locations and retention

| Store | Type | Controlled by | Deletion trigger |
|---|---|---|---|
| On-device SQLite | Per-user, device-local | Mobile app (Expo SQLite) | App uninstall, or account deletion (server cascade reflected after next sync). |
| Backend SQLite | Server-side, per-user rows | FastAPI service | `DELETE /auth/me` → full cascade delete. |
| Anthropic API | In-flight only | Anthropic (see §3) | Not stored beyond the API response. |
| Sentry | Error context | Sentry (see §3) | Per Sentry project retention policy (default 90 days). |

There is no separate analytics database, ad-targeting system, or data
warehouse. All production data lives in the backend SQLite file.

---

## 3. Third-party processors

### Anthropic (Claude API)

Chat history and live OBD readings are forwarded to the Anthropic Claude API to
generate AI responses. Anthropic's [usage policy](https://www.anthropic.com/legal/usage-policy)
and [privacy policy](https://www.anthropic.com/legal/privacy) govern how they
handle this data. As of this writing, Anthropic does not train on API customer
data by default.

### Google (OAuth)

Google Sign-In is supported. The app sends the Google ID token to the backend
for server-side verification. Only the `sub` (subject) and `email` claims are
retained; no profile picture, contacts, or other Google account data is stored.
Google's [privacy policy](https://policies.google.com/privacy) applies.

### Sentry

Crash reports are sent to Sentry when `SENTRY_DSN` is configured. PII scrubbing
is applied before transmission (see § 1.8). Sentry's
[privacy policy](https://sentry.io/privacy/) applies.

## 4. Security controls

| Control | Implementation |
|---|---|
| Passwords | bcrypt with per-password salt |
| Refresh tokens | SHA-256 digest only; raw token delivered once over HTTPS |
| Access tokens | HS256 JWT, 15-minute TTL |
| Transport | HTTPS (backend API) + WSS (WebSocket) |
| Auth rate limiting | 10 requests/minute per IP on all `/auth/*` endpoints |
| AI rate limiting | 20 turns/hour per authenticated user |
| Token budget | Configurable per-session token cap (`session_token_budget`) |
| Sentry PII scrub | `content`, `messages`, `system` keys redacted before event transmission |

---

## 5. User rights and controls

| Right | Mechanism |
|---|---|
| Access own data | `/auth/me` returns account email and locale. |
| Delete account | `DELETE /auth/me` — cascades to all sessions, messages, vehicles, and refresh tokens. |
| Correct vehicle data | Vehicles can be edited or soft-deleted via the sync API. |
| Opt out of crash reporting | Set `SENTRY_DSN=""` in the backend `.env` (operator-controlled). |

---

## 6. Children's data

The app is not directed at children under 13 (COPPA) or under 16 (GDPR). No
age-verification mechanism exists. If a minor's data is identified, it should
be deleted via the account deletion endpoint.

---

## 7. Data residency

The backend SQLite file resides on the server where the FastAPI service is
deployed. There is no multi-region replication in the current architecture. The
deployment region should be chosen to match the operator's data residency
requirements.
